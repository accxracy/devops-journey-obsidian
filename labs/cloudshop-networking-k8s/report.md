## 5. Объяснение различий между типами Service
- **ClusterIP** (используется в лабе по умолчанию): выделяет сервису внутренний IP-адрес. Делает сервис доступным *только* внутри кластера. Отличный выбор для внутреннего взаимодействия микросервисов.
- **NodePort**: открывает статический порт (обычно 30000-32767) на IP-адресе каждой рабочей ноды кластера. Трафик, приходящий на этот порт ноды, проксируется в сервис. Подходит для прямого внешнего доступа в тестовых средах.
- **LoadBalancer**: интегрируется с облачным провайдером (AWS, GCP, Yandex Cloud) для автоматического создания внешнего балансировщика нагрузки. Провайдер выдаёт публичный IP, который направляет трафик на NodePort'ы сервиса. Идеально для продакшена.

## 6. Анализ сетевой архитектуры и потоков трафика
Архитектура представляет собой защищённую микросервисную среду, разделённую на публичную (`cloudshop`) и приватную (`cloudshop-secure`) зоны.
- **Входящий (Ingress) трафик:** Клиенты обращаются к кластеру через внешний Ingress Controller (L7 балансировщик). Ingress читает HTTP-путь или Host и отправляет трафик напрямую на нужный Pod выбранного Service (ClusterIP).
- **Внутренний трафик (East-West):** Микросервисы общаются между собой исключительно через ClusterIP, используя DNS для обнаружения.
- **Управление доступом:** Трафик между зонами жёстко фильтруется CNI-плагином на сетевом уровне модели OSI (L3/L4). Любой трафик, не описанный явно в NetworkPolicy, уничтожается (Drop), предотвращая несанкционированный доступ к биллингу и БД при потенциальной компрометации публичного контура.

Для анализа сетевого трафика создан Pod `traffic-monitor` на основе
образа `nicolaka/netshoot`.

С помощью `nmap` выполнено сканирование `api-gateway-service`.
Обнаружен открытый TCP-порт `8080`.

Утилитой `curl` измерено время ответа `frontend-service`:

- DNS resolution: `0.001432` s;
- соединение: `0.001618` s;
- получение первого байта: `0.002481` s;
- полное время запроса: `0.002655` s.

Команды `ip route` и `traceroute` использованы для анализа маршрута
между Pod'ами. В однонодовом кластере Minikube трафик проходит через
виртуальную сеть Calico и имеет короткий маршрут.

С помощью `tcpdump` зафиксирован TCP-обмен между `traffic-monitor`
и `frontend-service`, включая установление соединения и передачу
HTTP-трафика.


## 7. Команды для отладки сетевых проблем
Основные команды, использованные для диагностики сети в Kubernetes:
- `kubectl get endpoints <service-name>` — проверка, привязаны ли к сервису реальные IP-адреса живых подов. Если список пуст, трафику некуда идти (ошибка селекторов).
- `kubectl exec -it <pod-name> -- nslookup <service-name>` — проверка работоспособности CoreDNS и Service Discovery.
- `kubectl exec -it <pod-name> -- nc -vz -w 5 <host> <port>` — проверка L4 TCP-соединения (открыт ли порт, не блокирует ли NetworkPolicy).
- `kubectl debug -it <pod-name> --image=nicolaka/netshoot` — запуск временного отладочного контейнера (ephemeral container) с сетевыми утилитами (ping, curl, nc, tcpdump) прямо внутри существующего пода без утилит, разделяя с ним одно сетевое пространство.
- `kubectl get pods --show-labels` и `kubectl get networkpolicy -o yaml` — анализ соответствия реальных меток подов и правил сетевых политик.
- `nmap -sT -Pn -p 1-10000 --open <service>` — сканирование открытых TCP-портов;
- `curl -w` — измерение времени DNS-резолюции, соединения и получения ответа;
- `ip route` — просмотр таблицы маршрутизации Pod'а;
- `traceroute <pod-ip>` — анализ маршрута до целевого Pod'а;
- `tcpdump -i any -nn` — захват и анализ сетевых пакетов.
